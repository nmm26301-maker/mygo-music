# 5.14.0 同一部手机的相册扫码登录

本轮从 5.13.0 和 GitHub main 继续，仅改进手机内完成扫码登录的流程，保留现有插件协议、二维码授权与账号保存逻辑。

## 使用流程

在播放器的登录窗口点击保存并打开扫码应用。二维码先保存到手机相册，再打开正确的账号应用。在该应用进入扫一扫，从相册选择刚保存的二维码，确认登录，再返回 MyGo Music。播放器继续等待服务端授权结果，不会把保存图片或打开应用误认为登录成功。

| 二维码种类 | 本机识别应用 |
| --- | --- |
| QQ 音乐的 QQ 授权码 | 手机 QQ |
| 微信授权码 | 微信 |
| 网易云音乐登录码 | 网易云音乐 |
| 酷狗登录码 | 酷狗音乐或酷狗概念版 |
| 哔哩哔哩登录码 | 哔哩哔哩 |

未知二维码只提供手动选择扫码应用的步骤。未安装对应应用时，保存仍可完成，并显示缺少哪个应用，登录等待继续。二维码变化或登录完成后，旧的打开动作不再生效。网页版登录窗口也提供保存并打开入口。

是否允许从相册识别特定登录码由对应平台的扫码应用决定。没有使用未经公开支持的扫一扫私有活动名或伪造应用授权；真实账号的最终确认仍需用户在对应应用完成。

## 参考与取舍

研究时间 2026-11-12。

* [guohuiyuan/go-music-dl](https://github.com/guohuiyuan/go-music-dl)，AGPL-3.0，最近维护 2026-11-09：现有二维码、状态轮询和成功保存 Cookie 的设计可供对照。其 Go 服务与多端界面依赖较重，本轮保留现有 Android 插件运行时，没有再增加一套后端。
* [NeteaseCloudMusicApiEnhanced/api-enhanced](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced)，MIT，最近维护 2026-11-06：二维码票据与授权结果是两个阶段。保留原插件的扫码确认、Cookie 校验及账号查询，不以识别出二维码代替授权完成。没有新增 Node 依赖，也未复制第三方实现。
* [Android 官方包可见性说明](https://developer.android.com/training/package-visibility)：仅声明需要打开的几个扫码应用。使用系统应用启动入口，不申请查询所有应用的权限。
* 应用包名对照相应开发者在小米应用商店中的条目；QR 的实际内容由已有 ZXing 组件解码和重新生成，保留原始登录票据及静区。

## 验证与恢复

PhoneQrChecks 验证按二维码识别正确的手机应用、误导域名不匹配、保存后才打开、缺失应用提示、实际切换到其他应用时保持登录等待、模拟授权回包后账号持久化，以及过期打开动作被拒绝。受控测试用系统设置页面代替真实扫码应用，不会假称用户账号已经完成实测。

原有 QrSaveUiChecks 继续检查原生及网页登录二维码保存到相册、PNG 可解码，以及保存后登录仍在等待。完整构建仍须运行原有歌词、插件、歌单、后台播放与市场检查，再验证从签名旧包覆盖安装。

从最新 GitHub 提交和 Actions 结果恢复，不重新初始化项目。5.13.0 移植清单中未完成的桌面辅助程序、个人账号与服务器验证等事项仍保留，见 [移植清单](full-port-status.md)。
